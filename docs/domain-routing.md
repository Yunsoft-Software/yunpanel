# Domain routing lifecycle

Domain canonical-hostname, alias, managed-HTTPS and redirect settings are revisioned desired state. An Owner first sends `POST /api/domains/:domainId/update-preview` with an exact `changes` object and then applies the same changes through `PATCH /api/domains/:domainId` with the preview SHA-256 and its full typed confirmation. Unknown fields, no-op requests, stale revisions, hostname conflicts, invalid parent relationships and active Domain/certificate jobs fail before mutation.

The editable fields are `primaryDomain`, `aliases`, `httpsMode`, `httpsRedirect` and `canonicalRedirect`. Hostnames use the existing IDN-to-ASCII canonicalization and global ownership checks. `httpsRedirect` is valid only with managed HTTPS. Switching to managed HTTPS defaults it on unless explicitly disabled; switching HTTPS off disables it. `canonicalRedirect` redirects every alias to the primary hostname while preserving the request URI. Before a certificate exists, canonical HTTP redirects remain HTTP so the primary server can continue serving the ACME challenge. Once TLS is attached, aliases redirect to the primary hostname on both HTTP and HTTPS, and the primary HTTP listener follows the explicit HTTPS-redirect policy.

Applying an update increments the desired revision and clears the staged revision. A hostname-set change or disabling HTTPS detaches the old certificate from the Domain; it does not expose or delete private-key material. The Domain must be staged and activated again. If the canonical hostname changed, activation atomically writes the new Nginx file and removes the prior active filename before `nginx -t` and reload. Validation, reload or preparation failure restores both filenames; durable recovery requires the new checksum to be active and the previous filename to be absent before marking the revision applied.

After a hostname change, a new managed certificate may replace the detached production record. The old record remains active until replacement issuance succeeds, then becomes `superseded` and is excluded from renewal. Certificate reconciliation verifies that the exact current primary hostname and aliases match the issued certificate before attachment. Nginx staging repeats the same exact coverage check, so stale or mismatched certificate metadata cannot enter a TLS config.

Every public Domain response contains a bounded `diagnosis` or `null`. Desired/staged/applied drift produces explicit stage or activation actions; missing managed TLS asks for a covering certificate; known Nginx failures map to authored remediation. Raw Nginx output, filesystem paths, certificate keys and arbitrary error text are not copied into the diagnosis. Persisted Domain store version 1 is hydrated with the legacy redirect behavior and applied canonical identity in memory, then written as version 2 only on a later mutation.

The common management audit records only Domain-scoped preview/apply identities and outcomes. Source tests cover request validation, migration, stale previews, concurrent job refusal, Nginx rendering/rollback, activation recovery, certificate replacement and protocol payloads. Real packaged Ubuntu, Nginx, DNS and browser/curl acceptance remains in `todo.md`; source tests are not host evidence.
